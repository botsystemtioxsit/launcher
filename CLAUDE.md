# CLAUDE.md

## What this is
«Ghost Shell Launcher» (раньше TIOXSIT Launcher; издатель по-прежнему TIOXSIT) — **нативное** Windows-приложение (C# / .NET 8 / WPF, один самодостаточный
`BattleLauncher.exe`). Не Electron, не веб-обёртка — владелец это прямо запретил; не
возвращать веб-технологии в сам лаунчер. Аккаунты + установка/обновление/запуск/удаление
«Тролль-Баттл» (репо `index.html`) и «БАТТЛ Админ» (репо `battle-admin-bot`) и «ВидеоЧат» (репо `videochat`, Electron-обёртка, как игра; ProductName «ВидеоЧат», видят все аккаунты игры, кроме токен-сессии). Тот же Firebase
(`zolotaya-kletka`, Spark, **без биллинга, никогда**), только REST, без SDK и без Firebase Auth.

## Layout (`Launcher/`)
- `MainWindow.xaml(.cs)` — весь интерфейс: вход, аккаунты, список приложений. Данные из базы и
  GitHub выводятся только как `Text`.
- `Services/Rtdb.cs` — REST к RTDB и Worker `/login-notify`; `Releases.cs` — версии из GitHub
  Releases (`latest.yml`); `Installer.cs` — реестр, скачивание + sha512, `/S`, запуск, удаление;
  `SelfUpdate.cs` — обновление самого лаунчера; `Catalog.cs` — список приложений и ролей;
  `AccountStore.cs` — `%APPDATA%\BattleLauncher\launcher.json`.

## Rules
- Три способа входа, как в `admin.html` (Telegram-вход не нужен): заявка по почте, токен доступа
  (`accessTokens/<token>`, сессия `Kind=token`, роль `token`, видит только админ-приложение),
  код устройства (`devicePairings/<код>`, `Paired=true`: пока нет `users/<id>/trustedDevices/<sha256(deviceId)>`
  — выходим). Секреты (токен, deviceId) только через `Secrets.Protect` (DPAPI), в логи и базу не писать.
- Планируется единый вход для будущих нативных приложений через общую сессию лаунчера — см. README
  («Единый вход»); не делать до отдельной просьбы, контракт сессии надо согласовать с владельцем.
- Вход по почте = заявка `users/<id>/loginRequests` как в игре/админке (`app: 'launcher'`; Worker для
  неизвестного `app` пишет общий текст). Секретов не хранится: только id/имя/роль. Роли в UI —
  удобство, не защита (база открыта на запись).
- Новое приложение = запись в `Catalog.cs`; в его репо нужен релиз с `latest.yml`
  (`electron-builder --publish always`). Если приложение станет нативным — научить `Installer`/`Releases` его формату.
- `FindInstalled` ищет `DisplayName == ProductName` в реестре и `<ProductName>.exe` в папке установки.
- Версию лаунчера поднимать в `Launcher.csproj` (`<Version>`) при каждом изменении, иначе релиз не обновится.
- Из этой среды .NET не поставить и Windows нет: компилирует и собирает GitHub Actions
  (смотреть логи job через GitHub MCP). Работу окна здесь проверить нельзя.

## Terminal (`Terminal/`, отдельный проект в этом же репозитории)
Нативная админ-панель (WPF, `TIOXSITTerminal.exe`). Общий код с лаунчером подключён ссылками на файлы
(`Net.cs`, `Rtdb.cs`, `AccountStore.cs`, `Catalog.cs` из `Launcher/Services`) — сессия и deviceId общие, поэтому вход
из лаунчера работает и в Терминале. Свои слои: `Terminal/Services/Db.cs` (REST + Worker `/set-status`),
`Data.cs` (чтение и разбор), `Models.cs`, `Ui.cs`; страницы — `MainWindow.Pages.cs`; `--screenshot=<папка>` — демо-снимки.
Правила: баны только через Worker (`Db.SetStatus`: аккаунт + deviceId доверенного устройства), все действия пишутся в
`logs` (`Db.Log`, без токенов и deviceId); опасные переключатели (аварийный режим, токены) — только Супердоступ, с
подтверждением; `config` целиком не читать (там секреты). Релиз Терминала — в релизе лаунчера (версия берётся из
`Launcher.csproj`); версию самого Терминала поднимать в `Terminal/Terminal.csproj`.

## Браузерная и EXE-версия (кнопки в «Приложениях»)
Всё, что лаунчер ставит сейчас, — «браузерная версия» (Electron-окна вокруг страниц): кнопка «Скачать браузерную версию».
Под ней «Скачать EXE-версию»: у приложения с `NativeExe` в `Catalog.cs` (сейчас «БАТТЛ Админ» → `TIOXSITTerminal.exe` из релиза лаунчера,
`Services/NativeInstaller.cs`: sha256 из `<файл>.sha256`, установка в `%LOCALAPPDATA%\Programs`, запись в «Установленные приложения»,
удаление через `BattleLauncher.exe --uninstall-native=<id>`) кнопка рабочая; у остальных заблокированная заглушка.
Новая нативная версия = положить `<Имя>.exe` + `.sha256` в релиз и прописать `NativeExe`/`NativeName` в `Catalog.cs`.

## Плагины (вкладка «Плагины», Windows 1.13.0)
Плагин — **отдельная программа**, которую человек скачивает из лаунчера только по кнопке (в лаунчер плагины **не вшиты**: владелец прямо этого потребовал, плагинов будет много и человек сам выбирает, какие ставить). Устроено как EXE-версия приложения: EXE + `.sha256` в релизе лаунчера, `NativeInstaller` ставит в `%LOCALAPPDATA%\Programs\<имя>`, только ярлык в «Пуск» (без рабочего стола, `AppDef.IsPlugin`), запись в «Установленные приложения». Список — раздел `plugins` в `catalog.json` (`id, name, desc, desktop{repo,tag,asset,name}`) + запасной список в `Catalog.DefaultPlugins()`; `Catalog.Plugins`, не `Catalog.Apps` (в «Приложения» плагины не попадают). Новый плагин = проект в `Plugins/<Имя>/` + шаги Publish/Checksum в `build-windows.yml` + запись в `catalog.json`. **Плагин обязан уметь вернуть всё, что менял** («Вернуть как было»), и выходить по событию `GhostShell.Plugin.Quit.<id>` (лаунчер просит выйти перед обновлением/удалением — `NativeInstaller.AskPluginToQuit`). Темы оформления (1.11.0) владелец велел **удалить** — не возвращать.

**Taskbar Plus** (`Plugins/TaskbarPlus/`, `TaskbarPlus.exe`, свой WPF-проект, namespace `TaskbarPlusApp`): окно настроек + движок, который держит вид панели, пока плагин запущен (закрытие окна прячет его в фон, «Выйти» снимает всё). Права администратора не нужны, DPI PerMonitorV2 (`app.manifest`).
- *Реестр HKCU* (`RegistrySettings.cs`, `Explorer\Advanced`: `TaskbarAl, ShowTaskViewButton, TaskbarDa, TaskbarMn, TaskbarSi, TaskbarSmallIcons, TaskbarGlomLevel(+MM), ShowSecondsInSystemClock, TaskbarAnimations`; `Search\SearchboxTaskbarMode`). Запись проверяется чтением обратно (Windows 11 тихо защищает `TaskbarDa` и др. — тогда честное сообщение + «Открыть настройки Windows» `ms-settings:taskbar`). `NeedsRestart` — после изменения предлагается перезапуск Проводника. Исходные значения — в `%APPDATA%\BattleLauncher\taskbar-plus.json` (тот же файл, что у 1.12.0).
- *Форма* (`Engine.cs`): `SetWindowRgn` на `Shell_TrayWnd`/`Shell_SecondaryTrayWnd`, цикл раз в 0,5 с (перепроверка региона раз в 10 с через `GetWindowRgnBox`). Формы (по картинкам владельца): `pill` (плавающая), `tab` (скруглён верх, низ уходит за край), `islands` (значки из UI Automation — Button-элементы панели; `IslandMode`: `each` — остров вокруг **каждого** значка, `group` — соседние склеиваются по зазору 16 px; `IslandStyle`: `float` плитки / `tab` скруглены сверху и прижаты к низу). Готовые варианты в окне: Обычная, Плавающая, Острова, Вкладка, Вкладки-острова, Только значки (= прозрачная панель без фона, зависит от размытия — на Windows 11 может не сработать). Только для панели внизу экрана. Если групп не нашлось — откат на `pill` с сообщением. Вырез снимается, когда форма выключена, а размытие осталось (`owned` — окна, на которые мы его поставили; `applied` при смене настроек забывается, а `owned` нет — иначе старый вырез оставался и значки обрезались полосками, ошибка 1.0.1). У `pill`/`tab` с отступом по бокам `KeepEdges` (по умолчанию да) находит через UI Automation часы/трей/виджеты и оставляет их отдельными островами — иначе они обрезаются формой и пропадают (так было в 1.0.0).
- *Размытие/прозрачность*: `SetWindowCompositionAttribute` (WCA_ACCENT_POLICY: 2 прозрачный, 3 размытие, 4 акрил). **Эксперимент**: на Windows 11 Проводник может закрывать эффект своим XAML-фоном (TranslucentTB для этого внедряется в Проводник — мы так не делаем).
- *Автоскрытие*: `SHAppBarMessage` ABM_SETSTATE; штатная анимация Windows (нужны `TaskbarAnimations=1` и системные «Эффекты анимации», `SPI_GETCLIENTAREAANIMATION`).
- *Не сделано* (честно): значки **справа** (Windows 11 не умеет; нужно внедрение в Проводник), собственная анимация выезда, настоящая прозрачность на Windows 11, надёжное изменение размера на самых новых сборках. Windows-эффекты этого окружения проверить нельзя — только CI-сборка; всё, что касается вида панели, проверяет владелец на своём компьютере и пишет, что не так.

## Вход необязателен, «Приложения» — только для админов (с 1.14.0)
Владелец: **лаунчер работает без входа в аккаунт**, а вкладка «Приложения» — **только у `admin` и `superadmin`** (токен доступа, модератор и обычный игрок её не видят; `IsStaff()` в `MainWindow.xaml.cs`). Окно (`MainView`) открыто всегда: «Плагины» видны всем, «Аккаунт» без входа показывает форму входа (`LoginView` теперь внутри правой части окна, кнопка в меню называется «Войти»), после входа — сведения об аккаунте. `ShowView("apps")` для не-админа сам уходит на «Плагины»; `LoadApps`, цикл уведомлений об обновлениях и `RequireAllowed` тоже проверяют `IsStaff` заново (роль могла смениться). Вход админа ведёт сразу в «Приложения». Режим `--screenshot` показывает форму входа через вкладку «Аккаунт».

## Taskbar Plus: что выяснилось на проверке у владельца (1.0.0 → 1.0.3)
- **Края формы «в пикселях»** — это свойство `SetWindowRgn`: у выреза нет сглаживания. Гладкие края возможны только если сделать панель по-настоящему прозрачной и рисовать форму своим окном позади панели; на Windows 11 прозрачность панели **не подтверждена** (скриншоты, где «фон исчез», на деле были остатками выреза). Проверять так: форма «Обычная» + «Прозрачная» — пропал ли фон панели.
- Остров ограничен скруглением ≤ 40% меньшей стороны (иначе получался круг); зазор снизу ≤ 25% высоты панели (иначе вырез съедал панель — значки не двигаются, поднять фигуру выше них нельзя).
- Окно плагина **зависало** после перезапуска Проводника: `SHAppBarMessage`, `taskkill` и рассылка `WM_SETTINGCHANGE` вызывались в потоке окна, а Проводник в этот момент не отвечает. Всё, что обращается к Проводнику или рассылает сообщения, — только в фоне (`Task.Run`), окно рисует кэшированное состояние (`autoHide`).
- Анимации автоскрытия нет даже при включённых «Эффектах анимации» — Windows 11 у владельца так и работает; своя плавная анимация не сделана (двигать панель программам нельзя).
- Виджеты программам не переключаются (защита Windows); «Группировка» и «Секунды в часах» работают.

## Taskbar Plus 1.0.4: автоскрытие и вынос прозрачности
- **Баг «панель не выезжает, когда приложение развёрнуто на весь экран»** (как у игр): при автоскрытии панель спрятана за нижним краем и торчит тонкой полоской, по ней Windows замечает курсор. Вырез (`SetWindowRgn`) эту полоску отрезал → панель не вызывалась. Теперь, пока панель скрыта (`Native.IsHiddenAtBottom`), вырез снимается, а когда она выезжает — возвращается (цикл раз в 150 мс). Любая форма, меняющая окно панели, обязана оставлять работающей полоску у края экрана.
- **Прозрачность и размытие из Taskbar Plus убраны** (владелец: «сделаем отдельным плагином, чтобы это работало на всех приложениях Windows»). Причины: на Windows 11 панель рисует фон XAML-ом, `SetWindowCompositionAttribute` его не убирает; настоящий способ — внедрение в Проводник через XAML Diagnostics (`InitializeXamlDiagnosticsEx` + свой TAP, как у TranslucentTB и Windhawk «Windows 11 Taskbar Styler»; цели стилей — `Rectangle#BackgroundFill`, `Taskbar.TaskListButton` и др., см. windows-11-taskbar-styling-guide). **План владельца: отдельный плагин прозрачности/размытия для окон всех приложений** (название не выбрано).

## Taskbar Plus 1.1.0: новый движок для Windows 11 (папка `Plugins/TaskbarPlus/Engine/`)
Зачем: вырез окна (`SetWindowRgn`) даёт «лесенку» на краях и не умеет прозрачность/размытие; Windows 11 рисует панель XAML-ом внутри Проводника. Движок — маленькая **C++ DLL** (`GhostShellTap.dll`), которая подключается к этому XAML через публичный интерфейс XAML Diagnostics (`xamlom.h` из Windows SDK, `InitializeXamlDiagnosticsEx` из `Windows.UI.Xaml.dll`) и меняет настоящие элементы панели (`Rectangle#BackgroundFill` — фон, `Rectangle#BackgroundStroke` — обводка, `Taskbar.TaskListButton` / `Taskbar.ExperienceToggleButton` / `Taskbar.SearchBoxButton` — значки, `SystemTray.SystemTrayFrame` и `Taskbar.AugmentedEntryPointButton` — края).
- **Лицензии: код чужих проектов не копировать.** Найденные открытые реализации этого приёма (TranslucentTB, UWPSpy, Windhawk-моды) — под GPL; разрешающих (MIT/Apache) примеров нет. Движок написан заново по публичному API Microsoft; приём (инъекция + TAP + подписка на дерево) — идея, а не код. Не вставлять сюда куски из GPL-репозиториев.
- **Как подключается** (`main.cpp`): C# вешает `SetWindowsHookEx(WH_CALLWNDPROC)` на поток `Shell_TrayWnd` с процедурой `GhostShellHookProc` из DLL → Windows сама грузит DLL в Проводник → хук один раз запускает поток → `InitializeXamlDiagnosticsEx("VisualDiagConnectionN", pid, nullptr, путь к DLL, CLSID, nullptr)` (до 60 попыток, имя подключения годится один раз) → XAML создаёт наш COM-класс (`DllGetClassObject` → `IObjectWithSite::SetSite` → `IXamlDiagnostics`) → в **отдельном потоке** (иначе взаимная блокировка) `IVisualTreeService::AdviseVisualTreeChange(callback)`; callback получает каждый элемент дерева (тип + имя) в потоке XAML. DLL закрепляется в процессе (`GET_MODULE_HANDLE_EX_FLAG_PIN`); вторая копия движка (старая версия) не запускается — мьютекс `Local\GhostShellTaskbarPlus.XamlEngine`, плагин пишет «перезапустите панель задач».
- **Всё, что трогает XAML, — только в потоке XAML** (`styler.cpp`): из других потоков — только `SetConfig` (кладёт настройки и увеличивает счётчик `g_cfgGen`), `WriteTree`, `GetStats`; поток XAML замечает новый счётчик на тике `xaml::DispatcherTimer` (250 мс) и применяет настройки. Очередь `DispatcherQueue` не нужна. Гладкие формы: плавающая = `RadiusX/Y` + `Margin` у `BackgroundFill`; «вкладка» = то же с отрицательным нижним отступом (нижние углы уходят за край); острова = `Border`ы, вставленные в `Panel`-родителя фона сразу над ним и под значками, позиции берутся через `TransformToVisual`, раз в 250 мс подстраиваются (`DispatcherTimer`); раз в секунду проверяется, что Windows не вернула свою кисть. Исходные значения запоминаются и возвращаются (`enabled=0`).
- **Обмен с плагином — только файлы** в `%APPDATA%\BattleLauncher\`: `taskbar-plus-engine.cfg` (плагин → движок, строки `ключ=значение`, движок читает раз в 0,3 с), `taskbar-plus-engine-status.txt` (движок → плагин: state/pid/tick/nodes/bgfill/…), `taskbar-plus-engine.log`, `taskbar-plus-xaml-tree.txt` (дерево элементов панели — по счётчику `dump=`; именно по нему подстраиваем под чужие сборки Windows, потому что структуру панели на другом компьютере увидеть нельзя), `taskbar-plus-engine-health.json`. Кнопка «Сохранить отчёт» (`XamlEngine.SaveReportAsync`) собирает всё это в `TaskbarPlus-report.txt` на рабочем столе — владелец присылает файл.
- **Защита от падений**: все точки входа DLL обёрнуты в `try/catch`; если Проводник дважды подряд закрылся в течение 90 с после подключения (не считая перезапуска, который сделал сам плагин — `NoteExplorerRestart`), движок блокируется (`health.Blocked`) до кнопки «Попробовать снова»; действует обычный способ (вырез). Пока новый движок не заработал (`Engines`: `xaml.Ready` = подключён и нашёл `BackgroundFill`), обычный способ остаётся включённым; когда заработал — обычный снимается.
- **DLL вложена в `TaskbarPlus.exe`** (`<EmbeddedResource LogicalName="GhostShellTap.dll">`), на ПК достаётся в `%LOCALAPPDATA%\GhostShell\TaskbarPlus\engine\GhostShellTap-<sha12>.dll` (имя по содержимому: старую копию, пока она нужна Проводнику, не трогаем). Собирается в `build-windows.yml` первым шагом (`cmake`, VS 2022, x64, статический CRT `/MT`, C++/WinRT-заголовки из Windows SDK). Только Windows 11 x64 (на ARM64 и Windows 10 — обычный способ). Из этой среды DLL не собрать и не проверить: компилирует CI, работу в Проводнике проверяет владелец и присылает отчёт.
- **Не сделано / дальше**: анимация автоскрытия (через XAML-анимации), значки справа, скругление кнопок по одной, скрытие виджетов политикой `AllowNewsAndInterests`. Прозрачность окон **всех** приложений — отдельный будущий плагин.

## Taskbar Plus 1.2.0: острова по отдельности, расположение групп, правила, отчёт одной кнопкой
Запросы владельца: (1) у каждого острова свой вид (угловатый, прозрачный, фиолетовый…); (2) часы, сеть, трей, скрытые значки — **всегда один объект**; (3) переносить системную область и значки слева / по центру / справа и менять местами. Прозрачность окон всех приложений — по-прежнему отдельный будущий плагин.
- **Три группы** (`styler.cpp`, `Kind`): `Widgets` (`Taskbar.AugmentedEntryPointButton`), `System` (всё, что `SystemTray.*`; остров — **объединение** всех её элементов, поэтому всегда один), `App` (`Taskbar.TaskListButton`, `ExperienceToggleButton`, `SearchBoxButton`). Номера в настройках: 0 виджеты, 1 система, 2 значки.
- **Правила классификации** — данные, а не код: строки `группа|тип|имя` (`*` — любые символы). Встроенные лежат в `DefaultRules()`; плагин при запуске скачивает `Plugins/TaskbarPlus/engine-rules.txt` из ветки `main` (raw.githubusercontent.com), кеширует в `%APPDATA%\BattleLauncher\taskbar-plus-engine-rules.txt` и передаёт движку строками `rule.N=` в `taskbar-plus-engine.cfg`; движок при смене правил заново разбирает уже увиденные элементы (`RescanAll`). **Чтобы подправить названия элементов под другую сборку Windows — поменять `engine-rules.txt` и слить в `main`, без нового выпуска плагина.** Фон/обводка/стили применяются к любому типу «поверхности» (`Shape`, `Border`, `Panel`, `Control`).
- **Расположение** (`ComputeShifts`): группа сдвигается `RenderTransform` (`TranslateTransform`, если у элемента уже был свой transform — оба в `TransformGroup`, при выходе возвращается прежний), поэтому нажатия идут за значками; окна Windows (календарь, «Пуск») могут открываться на прежнем месте. Сдвигаются только **верхние** элементы группы (`HasAncestorInKind` по `Node.parent`), вложенные едут с родителем. Двигаются лишь группы с явным выбором (слева/центр/справа); группы «как в Windows» — неподвижные опоры. Замеры «базовых» мест делаются при обнулённых сдвигах (`ResetShifts`), чтобы не зависеть от того, учитывает ли `TransformToVisual` собственный RenderTransform. Перерасчёт — только когда изменилась подпись размеров/смещений (`Signature`: `ActualWidth/Height/ActualOffset`, они от сдвигов не зависят).
- **Стили островов**: ключи `system`, `widgets`, `apps` (все значки), `app.<hex>` (один значок; ключ — по `AutomationId` значка через `FrameworkElementAutomationPeer`, иначе по имени без хвоста « - 2 окна»). В `taskbar-plus-engine.cfg`: `sty.<ключ>=радиус;цвет;прозрачность;режим;скрыт` (пустое поле — «как у всех»), `zone.widgets|system|apps=0..3`, `order=widgets,system,apps`, `edgeMargin`. Движок пишет список найденных островов в `taskbar-plus-engine-islands.txt` (`app|<ключ>|<hex имени>`), по нему окно плагина рисует список значков.
- **Отчёт одной кнопкой**: «Отправить отчёт разработчику» (`XamlEngine.UploadReportAsync`) делает `PUT` в общую базу `pluginReports/taskbar-plus/<id машины>.json`; `.github/workflows/sync-plugin-reports.yml` (cron раз в 3 часа + `workflow_dispatch`) складывает узел в `admin-logs/plugin-reports.json` этого репозитория — оттуда отчёт читаем мы. Из отчёта вычищаются имя пользователя и имя ПК; имена значков не отправляются. **После нажатия владельцем — запустить `sync-plugin-reports.yml` вручную и прочитать `admin-logs/plugin-reports.json`** (дерево элементов панели — главный источник для подстройки под его Windows).
- **Версия движка** (`GS_ENGINE_VERSION` в `Engine/common.h` = `XamlEngine.EngineVersion`): старая DLL остаётся в Проводнике до его перезапуска, новая рядом не запускается (мьютекс) — плагин пишет «перезапустите панель задач». Менять обе константы вместе при каждом изменении формата `cfg`/`status`.
- **Что показал первый запуск 1.1.0 у владельца**: движок подключился, но фон панели (`Rectangle#BackgroundFill`) не нашёл. В 1.2.0 добавлены: `IVisualTreeServiceCallback2` и `IVisualTreeService3` (как делают другие реализации), освобождение BSTR из `VisualElement`, диагностика в статусе (`rects`, `rectnames`, число найденных групп) и отчёт — по нему ищем настоящее имя/тип фона.

## Icon Plus 1.0.0 — третий плагин (`Plugins/IconPlus/`, `IconPlus.exe`, namespace `IconPlusApp`): значки Windows по-своему
Запрос владельца: плагин, который меняет значки — либо загрузкой готового набора, либо «как на Android»: задать цвет, и все значки его применяют; плюс поддержка сайта **https://vsthemes.org/ru/**, где иконки берут и скачивают. Работает как обычная программа (окно, без фонового процесса): значки хранятся в настройках Windows, закрытие плагина ничего не откатывает; «Вернуть как было» откатывает всё. Права администратора не нужны, кроме значка обычных папок (см. ниже).
- **Страницы окна:** «Цвет» (цвет + способ `mono`/`hue` + сила, какие цели перекрашивать, превью до→после, `Tint.cs`), «Наборы» (ввоз из архива/папки, автоподбор по именам файлов `Packs.Suggest`, ручной выбор значка для цели), «Сайт с иконками» (встроенный браузер WebView2), «Состояние» (что изменено, вернуть, обновить значки, перезапустить Проводник). Весь интерфейс кодом (как Color Plus); `--screenshot=<папка>` рисует страницы без сайта в PNG.
- **Цели** (`Targets.cs`): папка, диски (жёсткий/флешка/DVD/сетевой), «Этот компьютер», корзина (пустая/полная), сеть, папка пользователя, 12 групп типов файлов (список расширений в `Target.Extensions`), ярлыки рабочего стола / меню «Пуск» (по умолчанию выкл.) / закреплённые на панели задач. Ключевые слова (`Keywords`/`Reject`, русские и английские) — для подбора значков набора по именам файлов.
- **Что и куда пишется — проверено на раннере (не гадать заново):** значки «Этот компьютер»/корзина(`empty`/`full`)/сеть/папка пользователя — `HKCU\…\Explorer\CLSID\{…}\DefaultIcon`; диски — `HKCU\Software\Classes\Applications\Explorer.exe\Drives\<буква>\DefaultIcon`; типы файлов — `HKCU\Software\Classes\<ProgID>\DefaultIcon` (ProgID — выбор пользователя `UserChoice` и умолчание `HKCR\.ext`); ярлыки — настоящим объектом `IShellLink` (`Shortcuts.cs`: загрузка+сохранение не теряют остальное, в том числе идентификатор программы; через WScript.Shell не делать). **Обычные папки без прав администратора поменять нельзя**: `HKCU\Software\Classes\Directory|Folder\DefaultIcon` и `HKCU\…\Explorer\Shell Icons` Проводник игнорирует; работает только `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\Shell Icons` значения «3» (закрытая) и «4» (открытая) — плагин запускает свою копию с `runas` (`FolderIcon.cs`, ключи `--folder-icon=<ico>` / `--folder-icon-restore`), прежние значения лежат тут же (`IconPlus.Backup.3/4`), `IconPlus.Created` — ключ создан нами. Часть значков (файлы, ярлыки) обновляется сразу после `SHChangeNotify` + `ie4uinit.exe -ClearIconCache`/`-show` (`Native.RefreshIconCache`), а панель слева, «Этот компьютер», диски и папки — **только после перезапуска Проводника**: после применения окно спрашивает (`AskExplorerRestart`).
- **Исходный значок для перекраски** берётся у системы один раз и запоминается в `state.Sources` (потом, когда значок уже заменён, красится оригинал): CLSID — из `HKLM\…\CLSID\{…}\DefaultIcon`; типы файлов — `AssocQueryString(ASSOCSTR_DEFAULTICON)` (SHGetFileInfo(ICONLOCATION) для файлов возвращает пусто); ярлыки — `IShellLink.GetIconLocation`, иначе значок цели. Перекрашенные значки — `.ico` (7 размеров 16–256, PNG внутри) в `%APPDATA%\BattleLauncher\icon-plus\generated\<хеш>.ico`.
- **Откат** (`State.cs`): каждое прежнее значение реестра запоминается (`RegChange`: путь, имя, было ли, значение, **вид значения** — `REG_EXPAND_SZ` с `%SystemRoot%` нельзя возвращать как `REG_SZ`: первый тест так сломал значок корзины), создававшиеся нами ветки убираются снизу вверх; ярлыки — `LnkChange`. Состояние в `%APPDATA%\BattleLauncher\icon-plus\state.json`, наборы — `packs\<имя>\*.ico`.
- **Сайт vsthemes.org — только глазами человека.** В его `robots.txt` для всех роботов закрыты `/download/`, `/ru/download/`, `/go/` (и `Disallow: /*?`), запросы с раннера получают `429`, браузер видит проверку Cloudflare («Подтвердите, что вы человек»). Поэтому плагин **ничего не скачивает с сайта сам и не разбирает его страницы**: вкладка «Сайт» — обычный браузер WebView2 (профиль в `%LOCALAPPDATA%\GhostShell\IconPlus\webview`); человек сам проходит проверку и жмёт «Скачать», плагин перехватывает именно это скачивание (`DownloadStarting`, `Handled = true`, файл в `…\icon-plus\downloads\<время>\`) и ввозит как набор (`Packs.Import`). Из архива берутся **только `.ico` и `.png`** (zip, 7z, rar через SharpCompress, MIT; лимиты: 5000 файлов, 400 МБ, 25 МБ на файл; имена очищаются, пути не используются, пароль архива вводится вручную); `.exe/.msi/.7tsp/.ip/.theme/…` не запускаются и не ввозятся (сообщение «это не набор значков»). ## Значки программ Ghost Shell и Icon Plus 1.1.0 (по двум снимкам владельца без слов: «Пуск» и рабочий стол)
- **Что показали снимки:** у лаунчера, Терминала и всех плагинов в «Пуске» одинаковые значки-заглушки, а ярлык «TIOXSIT Launcher» на рабочем столе и на панели задач — белый пустой лист. Теперь у каждого проекта свой значок `app.ico` + `<ApplicationIcon>app.ico</ApplicationIcon>` (лаунчер — призрак, Терминал — окно с `>_`, Taskbar Plus — панель с островами, Color Plus — три круга, Icon Plus — сетка значков; киберпанк-палитра владельца). **Рисует `tools/make-icons.py` (Pillow)** — менять значки правкой скрипта и перезапуском, а не руками; готовые `.ico` лежат рядом с проектами. Новому проекту/плагину — свой `app.ico` и запись в `JOBS`.

Теперь цели `lnk-desktop-all`, `lnk-start-all` (и `lnk-start` для личного «Пуска») включены по умолчанию; всё, что требует прав администратора (значок обычных папок + ярлыки «для всех»), собирается в **одно задание `MachineJob`** (`Machine.cs`): `IconPlus.exe --machine=<файл задания>` запускается с `runas` — **одно окно «Разрешить?»**; прежние значки ярлыков запоминаются в `%APPDATA%\BattleLauncher\icon-plus\machine-lnk-backup.json` (пишет сам помощник), результат — `machine-result.txt`; возврат — то же задание с `Restore = true`. Старый Color Plus (1.x, огромный: вкладки «Окна / Панель задач / Выделение / Заголовки», прозрачность, размытие, «стекло», правила по программам) владелец велел **удалить и сделать заново, намного проще**: «ровно такой же по функционалу, как у Samsung (One UI, Good Lock, Theme Park): виден интерфейс, через него редактируешь, смотришь результат и применяешь; никаких пересложных вкладок». - **Устройство (`Plugins/ColorPlus/`, `ColorPlus.exe`, namespace `ColorPlusApp`, один экран):** живой **предпросмотр** (`Preview.cs`: выдуманный рабочий стол с двумя окнами и панелью) → **«Готовые темы»** (кнопки с цветом) → **«Свой цвет»** (образцы, `#RRGGBB`, ползунки «Оттенок» и «Яркость») → **две галочки** «Окна и выделение» и «Панель задач» → **«Применить»** / **«Вернуть как было»**. Пока не нажато «Применить», в Windows не меняется ничего — только предпросмотр. Больше настроек не добавлять без просьбы владельца (он просил именно проще).

(2) **Акцент и выделение** — запись реестра: `DWM\AccentColor`, `ColorizationColor/Afterglow`, `Explorer\Accent\AccentPalette` (8 оттенков в HSL, байты `R G B 00`), `Personalize\ColorPrevalence=0` («Пуск» и панель задач акцентом **не** красятся), `Control Panel\Colors\Hilight/HilightText` + `SetSysColors`, рассылка `WM_SETTINGCHANGE "ImmersiveColorSet"` и `WM_DWMCOLORIZATIONCOLORCHANGED`; на раннере значения пишутся и возвращаются, но **видимого эффекта этого на раннере нет** (проверять у владельца). Всё прежнее запоминается до первого изменения (`color-plus-originals.json`) и возвращается кнопкой.
- **Серая панель у владельца (2.1.0) — причина:** в его `taskbar-plus-settings.json` было `UseXaml:false` («Новый движок» выключен), Taskbar Plus резал панель в «пилюлю» обычным способом (`SetWindowRgn`) — а красить может только движок. Это было видно по отчёту Color Plus (`UseXaml:false`, «движок: (нет файла)»), размер пилюли совпал с `SideMargin 600`. Теперь `TaskbarPlusControl` различает состояния (не установлен / не запущен / движок выключен / подключается / готов), показывает их в окне и при «Применить» с галочкой «Панель задач» **сам включает движок**: выставляет `UseXaml` и `XamlConsentShown` в настройках Taskbar Plus, просит его выйти (событие `GhostShell.Plugin.Quit.taskbar-plus`), запускает `%LOCALAPPDATA%\Programs\TaskbarPlus\TaskbarPlus.exe --background` и ждёт `state=ready` (до 90 с). Обычное окно панели при этом по-прежнему не красится.
- **Панель задач:** Color Plus пишет `color-plus-taskbar.json` (`Active, BgMode solid, BgColor, BgOpacity 85`) — **цвет получают острова Taskbar Plus**, окно обычной панели Windows не красится и не размывается никогда; пока Taskbar Plus не запущен (движок «ready», `EngineState()`), панель остаётся как в Windows, а окно Color Plus пишет об этом.

- **Проверка:** сценарий `colorplus` в `test-windows.yml` (`tests/e2e/color-plus.ps1`, ветка `ci-e2e-colorplus`): значения реестра до/после/после возврата, окна Проводника и Блокнота (старое и новое), острова Taskbar Plus с цветом. Служебные ключи: `--apply=#RRGGBB [--no-windows] [--no-taskbar]`, `--revert`, `--screenshot=<папка>`.
- **Канал с Taskbar Plus:** Taskbar Plus читает `%APPDATA%\BattleLauncher\color-plus-taskbar.json` (`ColorPlusLink`, формат `Active, BgMode default|solid|clear|acrylic, BgColor, BgOpacity, HideStroke`) — его пишет Color Plus 2. Тесты панели в `run.ps1` кладут этот файл вручную.
- **Правила для новой версии (всё это владелец уже говорил и сердился, когда нарушали):** (1) **окно обычной панели Windows не красить и не размывать никогда** (ни акрилом, ни `SetWindowCompositionAttribute`): цвет получают только острова нашего Taskbar Plus через его движок, обычная панель остаётся прозрачной; без запущенного Taskbar Plus панель Windows не трогать совсем (после перезапуска Проводника движок подключается не сразу — залитое окно давало розовую вспышку и розовую панель целиком); предпросмотр цвета обязан показывать то же, что будет на деле. (2) Эффект, который **перехватывает мышь или рисует мимо программы** (цветовой ключ, подложка под прозрачным слоем), — не общей настройкой, а только по явному правилу программы; игры и 3D (классы `GLFW*`, `SDL_app`, `Unity*`, `Unreal*`, подгруженные `opengl32/vulkan/d3d12/steam_api`), Steam, Wallpaper Engine, Lively, Rainmeter, OBS не трогать никогда; окна без своей строки заголовка (Qt/CEF) — только по правилу. (3) Всё, что меняли, помечать (`SetProp`) и возвращать при выходе и при следующем запуске, если плагин убит. (4) Подложка окна цвета оттенка красит текст, если у окна GDI-текст на растянутой рамке (`DwmExtendFrameIntoClientArea(-1)`), — Проводнику и диалогам «растянуть на всё окно» не ставить; цвет текста выделения по умолчанию «Авто» (не трогать), чтобы розовое на розовом не читалось. (5) Chrome/Edge/Electron/магазинные приложения рисуют через DirectComposition: «только фон прозрачный» снаружи невозможен, честно сказать об этом в окне. (6) Конструктор с живым предпросмотром и отложенным «Применить» (как в Theme Park на Samsung) — понравился владельцу, оставить такой подход. (7) Акцентный цвет Windows не должен красить меню «Пуск» и панель задач; Icon Plus после перезапуска Проводника не должен менять цвет панели.

## Gateway Plus 1.0.0 — шестой плагин (`Plugins/GatewayPlus/`, `GatewayPlus.exe`, namespace `GatewayPlusApp`, id `gateway-plus`): шлюз (WireGuard)
Запрос владельца: «программа, которая маскирует устройство: сайт думает, что компьютер в Германии, свой IP; шлюз, через который течёт трафик». Это клиент VPN на WireGuard. **Что плагин делает и чего нет:** сам по себе IP в Германии он не создаёт — нужна **точка выхода** (сервер в Германии) — это деньги и аккаунт владельца, их мы не создаём: (1) свой маленький VPS в Германии (несколько евро в месяц) — плагин даёт готовый **скрипт сервера** (`Resources/server-setup.sh`, вшит в exe, кнопка «Скопировать скрипт»; Ubuntu 22.04/24.04 / Debian 12: ставит `wireguard`, NAT через `iptables`, `ip_forward`, открывает порт 51820/udp в `ufw`, печатает готовый конфиг клиента между двумя линиями; проверен `bash -n` и сухим прогоном с подставными командами, на настоящем сервере не запускался); (2) конфиг WireGuard от платного VPN-сервиса. Бесплатных VPN не советуем (честно сказано в окне); Tor/WARP не делали.
- **Устройство.** Окно (один экран): «Сейчас вас видят так» (внешний IP, страна, город, часовой пояс сайта — `IpInfo`, сервис `ipwho.is`) → «Шлюз» (установка WireGuard, профили, «Подключить»/«Отключить», «＋ Добавить конфиг…») → «Свой сервер в Германии» (шаги + скрипт) → «Что шлюз скрывает, а что нет» → «Вернуть как было». Туннель — служба **официального WireGuard для Windows** (`C:\Program Files\WireGuard\wireguard.exe /installtunnelservice <conf>` → служба `WireGuardTunnel$<имя>`; плагин закрывается — шлюз продолжает работать, он не зависит от плагина). С `AllowedIPs = 0.0.0.0/0` WireGuard сам включает защиту от утечек (закрывает трафик мимо туннеля), поэтому отдельного kill switch не пишем.
- **Установка WireGuard** (`Wg.InstallAsync`) только по кнопке: официальный `https://download.wireguard.com/windows-client/wireguard-installer.exe`, **подпись проверяется** (`X509Certificate.CreateFromSignedFile`, цепочка доверена, имя содержит WireGuard), запуск с `runas`.
- **Права администратора** нужны только для службы туннеля: действия `connect/disconnect/cleanup` выполняет тот же `GatewayPlus.exe --helper=<файл задания>`, запущенный с `runas` (`Helper.RunAsync`, итог — файл `result.json`); один запрос Windows на действие. Конфиг для службы кладётся в `%ProgramData%\GhostShell\GatewayPlus\<имя>.conf`, папка закрыта `icacls` (`*S-1-5-18` и `*S-1-5-32-544`, без наследования) — внутри закрытый ключ. Временный файл с конфигом в `%TEMP%` удаляется сразу после действия.
- **Безопасность конфига** (`Store.Validate`): нужны `[Interface]`, `[Peer]`, `PrivateKey`, `PublicKey`, `Endpoint`; **`PreUp/PostUp/PreDown/PostDown` отклоняются** (их выполняла бы служба от имени системы); посторонние строки отклоняются; имя туннеля — `[A-Za-z0-9_=+.-]{1,32}`. Профили хранятся под **DPAPI** (`ProtectedData`, `CurrentUser`) в `%APPDATA%\BattleLauncher\gateway-plus\profiles\<имя>.dat`; закрытый ключ нигде не пишется в логи и в отчёты.
- **«Вернуть как было»:** `cleanup` — снимает службы всех наших туннелей, чистит папку ProgramData; сохранённые профили остаются (это данные владельца).
- **Проверка на раннере:** сценарий `gateway` (`tests/e2e/gateway-plus.ps1`, ветка `ci-e2e-gateway`): снимок окна, проверка конфигов/имён/шифрования профиля/встроенного скрипта (`bash -n`), установка настоящего WireGuard из MSI (подпись MSI проверяется), создание туннеля `citest` на несуществующий сервер **с маленькой сетью в `AllowedIPs`** (интернет раннера не трогается): служба работает, появился адаптер, права на папку без «Пользователей», после отключения службы и файла нет. **Не проверено без ПК владельца и без настоящего сервера:** рукопожатие с настоящим сервером, скорость, поведение при обрыве, утечки DNS/IPv6 на его сборке Windows, работа скрипта на настоящем VPS.

Что можно, а чего нельзя, сказано владельцу прямо: **IP-адрес расширением не меняется** (сайт видит адрес, с которого пришёл пакет) — для IP нужен шлюз Gateway Plus и сервер в нужной стране; расширение меняет только то, что браузер сообщает сам (часовой пояс, язык, местоположение, адрес через WebRTC). Только Chromium (Chrome, Edge, Brave, Opera, Vivaldi), Firefox нет.
- **Где лежит:** `BrowserPlugins/MaskPlus/` (манифест MV3, `background.js`, `engine.js`, окно `popup.*`, значки `icons/`), всё, что генерируется, — `c/<СТРАНА>.js` (49 файлов), `f/<tlg>.js` (8 файлов флагов), `countries.js`; **руками их не править** — `python3 tools/mask-plus/generate.py` из `tools/mask-plus/countries.json` (там же проверка поясов через Intl); значки — `tools/mask-plus/make-icon.py`; упаковка — `tools/mask-plus/pack.py <папка>` (детерминированный zip: даты фиксированы, LF, сортировка — иначе лаунчер видел бы «обновление» при каждой сборке, он сравнивает `.sha256`). Новая страна = запись в `countries.json` + generate.py.
- **Как подмена попадает на страницу:** скрипты, которые работают ДО скриптов страницы (`world: MAIN`, `document_start`, `allFrames`, `matchOriginAsFallback`), хранилища читать не могут, поэтому настройки «запечены» в файлы: фон регистрирует (`chrome.scripting.registerContentScripts`, id `mask-plus`) три файла подряд — `c/<страна>.js` → `f/<тлг>.js` → `engine.js` (они передают настройки через временное свойство `__gsmask`, движок его сразу удаляет). Исключённые сайты — `excludeMatches`. Окно (`popup.js`) только пишет в `chrome.storage.local` (`enabled, cc, tz, lang, geo, webrtc, excluded`), фон реагирует на `storage.onChanged`: перерегистрирует скрипты, ставит правило declarativeNetRequest (Accept-Language для всех запросов, исключённые сайты — `excludedRequestDomains/InitiatorDomains`), включает `chrome.privacy.network.webRTCIPHandlingPolicy = default_public_interface_only` (не `disable_non_proxied_udp`: тот ломает звонки, в том числе ВидеоЧат) и рисует код страны на значке. Вкладки, открытые до смены, не меняются сами — окно показывает «что видит эта вкладка» (спрашивает у самой страницы в её мире) и предлагает обновить.
- **Что подменяет `engine.js`:** `Date` (прокси конструктора: `new Date(2024,0,1)` и ISO-строка без пояса — местное время выбранной страны; все местные получатели/установщики, `toString/toDateString/toTimeString` в формате V8 с названием пояса «как у родного», `toLocale*String`, `getTimezoneOffset`; переход на летнее время и «двойной/пропавший» час — как в стандарте), `Intl.*` (язык и пояс по умолчанию через прокси конструкторов), `Number/BigInt.toLocaleString`, `String.localeCompare`, `Temporal.Now`, `navigator.language(s)` (замороженный массив, один и тот же объект), `navigator.geolocation` (позиция у центра города ±1–2 км, настоящие типы `GeolocationPosition/Coordinates`, `watchPosition/clearWatch`). Подделки выглядят родными (`Function.prototype.toString` → `[native code]`, имена и `length`, методы без `prototype`); на лету подменяется и `contentWindow/contentDocument` только что созданных iframe (иначе страницы берут «чистые» функции из пустого iframe). **Не покрывается:** Web Worker и Service Worker (свой `Intl`/`Date` — выдадут настоящий пояс), tz-строки вроде «Jan 1, 2024 10:00» (разбираются родным способом), `Date` до 1970 года — название пояса в скобках может отличаться, расхождение с настоящим IP (сайты сверяют IP-страну и пояс — поэтому нужен шлюз), прочие отпечатки (шрифты, экран, canvas).
- **Проверено в настоящем Chromium (не на Windows):** `tests/mask-plus/run.js` — сравнение с родной эмуляцией Playwright для всех 49 стран, ~150 вызовов на страну (48 из 49 полностью совпали; `az-AZ` — отличается только список `Intl.ListFormat` из-за данных ICU в тестовой сборке); `tests/mask-plus/run2.js` — 33 функциональные проверки (заголовок, геолокация, iframe, переключатели, исключения, WebRTC, выключение, окно). Запуск — в README рядом. **Не проверено без ПК владельца:** его настоящий Chrome/Edge (версия, сторонние расширения, которые тоже держат WebRTC), вид окна расширения на его экране.
- **Вкладки в «Плагинах» лаунчера** (`PluginsTabPc/PluginsTabBrowser`, `SetPluginsTab`): «Для компьютера» — прежний список (EXE-плагины), «Для браузера» — раздел `browserPlugins` в `catalog.json` (`id, name, desc, browsers, zip{repo,tag,asset}`; `Catalog.ParseBrowserPlugins`, запасной список `DefaultBrowserPlugins()`). Новое расширение = папка в `BrowserPlugins/`, шаг упаковки в `build-windows.yml` (zip + `.sha256` в релиз, как у MaskPlus), запись в `catalog.json` и в запасной список.
- **`BrowserInstaller`:** zip из релиза (`Net.IsTrustedDownload`, проверка sha256 по `<asset>.sha256`), безопасная распаковка в `%LOCALAPPDATA%\GhostShell\BrowserPlugins\<id>` (только `.js .json .html .css .png .jpg .svg .ico .txt .md .woff(2)`, пути строго внутри папки, ≤3000 файлов, ≤20 МБ файл, ≤80 МБ всего, обязателен `manifest.json`); сумма установленной версии лежит рядом (`<id>.sha256`) — по ней «Есть обновление». **Подключает папку в браузере сам человек** («Режим разработчика» → «Загрузить распакованное расширение»): установка расширений в браузер снаружи Windows не даёт, и мы это не обходим (политики ExtensionInstallForcelist требуют прав администратора и размещённого .crx — не делаем). После обновления из лаунчера в браузере нужно нажать круглую стрелку у расширения. Теперь: (1) **релиз берётся прямыми адресами** `https://github.com/<владелец>/<репо>/releases/latest/download/<файл>[.sha256]` (или `…/download/<тег>/…`) — лимита нет; так же у `NativeInstaller.Latest` (плагины для компьютера; `NativeRelease.Tag` — «latest» или тег, нигде не показывается); (2) кнопка «Скачать» **всегда включена** (и у плагинов для компьютера): нажатие заново проверяет релиз и скачивает, два повтора при коротком сбое сети; (3) причина неудачи — простыми словами (`BrowserInstaller.Explain`: 404 «нет файла в релизе», 403/429 «слишком много запросов», нет связи, время вышло, нет права записи) — **красным текстом в карточке** (`browserErrors`, не пропадает через 5 секунд, как сообщение внизу), а не только всплывающим сообщением; (4) рядом кнопка **«Скачать файл вручную»** (`ZipUrl` в браузере) на случай, если из лаунчера не выходит совсем. Самопроверка `--selftest-browser` теперь проверяет и эти пути (несуществующий файл → `null`, понятная причина, нет мусора после сбоя, плагин для компьютера находится прямым адресом). **Правило на будущее:** новые проверки релизов — только прямыми адресами, не через `api.github.com`; ошибку никогда не глотать молча — показывать причину в интерфейсе.

## Skin Loader 1.0.0 — седьмой плагин (`Plugins/SkinLoader/`, `SkinLoader.exe`, namespace `SkinLoaderApp`, id `skin-loader`): скины Windows
Запрос владельца: «собрать всё в скин Windows и выкладывать — как Wallpaper Engine, но со скинами: Taskbar Plus, Color Plus, Icon Plus, Wallpaper Plus, Cursor Plus — поставить галочки, что используется, скин собирается и сам применяется; плюс кнопка "настроить по-своему / кодом"; там, куда выкладываются скины, — **Skin Loader**; пространство для тонкой настройки кодом — **Code Engine Plus**». Делается этапами. **Этап 1 (этот): локально** — сборка, библиотека, применение, откат, файл `.ghostskin` для обмена. **Дальше:** галерея (публикация/скачивание через общую базу, жалобы, модерация в панели), затем Code Engine Plus (кнопка «Настроить кодом» в карточке скина появляется сама, когда установлен `%LOCALAPPDATA%\Programs\CodeEnginePlus\CodeEnginePlus.exe`; запуск `CodeEnginePlus.exe --skin="<skin.json>"`).
- **Скин — данные, не программа** (`Skin.cs`, `SkinSchema`): файл `skin.json` (`format:1`, `name`, `author`, `description`, `created`, `parts{taskbar,color,icons,wallpaper,cursor}`) — только значения из белого списка: цвета `#RRGGBB`, числа в пределах, имена форм/режимов из фиксированных списков, идентификатор встроенных (`b-…`) или каталожных (`c-…`) обоев. **Ни путей, ни команд, ни кода.** Всё чужое (импорт файла, потом галерея) проходит `Skin.Parse`: неизвестное выбрасывается, числа зажимаются, неверные типы → значение по умолчанию, текст чистится от управляющих и «перевёрнутых» (RTL) символов, файл ≤ 64 КБ, вложенность ≤ 8; `mine:<id>` (свой нарисованный курсор) и обои `u-…` (свои файлы человека) в скин не входят. Часть = полный набор ключей (недостающее — по умолчанию), поэтому очищенный скин после записи и чтения не меняется. Новая настройка = ключ в `CleanPart` + строки в `Capture.FromSettings` и `Applier.ApplyPart`.
- **Сбор** (`Capture.cs`): из файлов настроек плагинов в `%APPDATA%\BattleLauncher\` (`taskbar-plus-settings.json`, `color-plus-settings.json`, `icon-plus\settings.json`, `wallpaper-plus-settings.json`, `cursor-plus\settings.json`; ключи PascalCase → в скине camelCase) через ту же очистку. «Используется» = плагин что-то применял (`Applied`, `Shape != none`, `Active`, есть `icon-plus\state.json`); отмечены галочками по умолчанию именно такие части.
- **Применение** (`Applier.cs`): на часть — один плагин, **порядок:** панель → цвет → обои → курсор → значки. Всегда «сначала `AskQuit` (событие `GhostShell.Plugin.Quit.<id>`, ждём выхода), потом запись в его файл настроек (`Plugins.MergeSettings`: меняются только перечисленные поля, остальное сохраняется, файл пишется через `.tmp`), потом запуск плагина с его же ключом»: `TaskbarPlus.exe --background` (читает сохранённое; движок включается `UseXaml=true` только если форма не `none` или группы сдвинуты, `XamlConsentShown=true` — согласие даёт окно подтверждения Skin Loader), `ColorPlus.exe --apply=#hex [--no-windows] [--no-taskbar]`, `WallpaperPlus.exe --apply=<id>` (+ `Fit`, `Fps`), `CursorPlus.exe --apply`, `IconPlus.exe --apply-color=#hex` (+ `Style`, `Strength`; Проводник может перезапуститься, Windows может спросить разрешение для значков «для всех»). Подтверждение применения происходит по файлу настроек плагина (`Applied`/`Active`), с таймаутом и понятным сообщением. **Откат** (`RevertAll`) — собственный откат каждого плагина: `--revert` (курсор, цвет), `--restore` (значки), выход обоев + `Active=""`, панель — `Shape=none`, `UseXaml=false`, зоны по умолчанию и выход Taskbar Plus (если что-то осталось — «Вернуть как было» в самом Taskbar Plus; движок в Проводнике до его перезапуска может висеть). Запись «что применено» — `skin-loader\applied.json`.
- **Библиотека и файл** (`Library.cs`): `%APPDATA%\BattleLauncher\skin-loader\skins\<s-…>\{skin.json, preview.jpg}`; `.ghostskin` — zip из этих двух файлов. **Импорт**: файл ≤ 2 МБ, ≤ 8 вложений, берутся только `skin.json` и `preview.*` (остальное игнорируется с замечанием), картинка разбирается и **пересохраняется** как JPEG ≤ 120 КБ (`Shots.Sanitize`), скин очищается. Превью — «Снять экран» (окно сворачивается на 0,9 с, GDI `BitBlt` с `CAPTUREBLT`) или файл.

## Gateway Plus 2.0.0: личный VPN «сделай сам», аккаунты и блокировка (лаунчер 1.36.0)
Запрос владельца (голосом, «GTA Plus» = Gateway Plus): «чтобы человек сам устанавливал — инструмент для создания личного VPN; отдельная база на Firebase и отдельная система аккаунтов, чтобы люди логинились; подвязка к терминалу, чтобы можно было заблокировать доступ; если использует в коммерческих целях — бан, проект бесплатный».
- **Что сделано в плагине** (`Plugins/GatewayPlus/`): (1) **Аккаунт** (`Account.cs`, `AccountWindow.cs`): без пароля и почты — человеку выдаётся ключ `GW-XXXX-…` (160 случайных бит, base32, 8 групп по 4), номер аккаунта в базе = первые 24 знака sha256 от ключа (`IdOf`), ключ хранится на компьютере под DPAPI (`account.dat`), показывается один раз при создании и потом кнопкой «Показать ключ»; вход на другом компьютере — «У меня есть ключ» (если записи в базе уже нет — создаётся заново с введённым именем). Без Firebase Auth. (2) **Правила** (`Terms.cs`, `Terms.Version`): окно показывается при создании аккаунта, без галочки «согласен» аккаунт не создаётся; поднял версию — у всех при следующем «Подключить»/мастере откроется окно согласия. Главное правило: только личное использование, коммерция (продажа/сдача в аренду доступа, платный сервис) — бан. (3) **Блокировка** (`Cloud.cs`): перед «Подключить», мастером и «Скопировать скрипт» (`EnsureAllowedAsync`), при открытии окна и раз в 10 минут плагин читает `gatewayBlocks/<id>` и `gatewayBlockedDevices/<dev>` (dev = 32 hex от MachineGuid с солью, `Account.DeviceHash`); если заблокирован — шлюз и мастер не работают, а если шлюз уже включён — он отключается сам (одно окно разрешения Windows). **«Отключить» и «Вернуть как было» блокировка не трогает никогда.** Нет связи → последний известный ответ (`access.json`), так что отключением интернета блокировку не обойти. Новый аккаунт на заблокированном компьютере не создаётся. Раз в запуск и после мастера уходит «пульс» (`lastSeen`, версия, число профилей, принятые правила). (4) **Мастер «Создать свой VPN»** (`Provisioner.cs`, `WizardWindow.cs`): адрес/порт/пользователь + пароль или файл ключа SSH → плагин по SSH (библиотека SSH.NET, MIT) проверяет систему (Ubuntu 22.04/24.04, Debian 12; нужен root или sudo без пароля), при уже настроенном WireGuard спрашивает (новые ключи сломают старые конфиги), передаёт `server-setup.sh` одной командой (base64, без SFTP), запускает его, забирает конфиг (между строками «НАЧАЛО КОНФИГА»/«КОНЕЦ КОНФИГА»; **сам конфиг с закрытым ключом в журнал окна не выводится**), проверяет его `Store.Validate` и сохраняет профиль. Пароль нигде не сохраняется (только в памяти на время установки). Отпечаток сервера: первый раз — окно с подтверждением, потом запоминается (`known-hosts.json`), если изменился — отдельное предупреждение. Скрипт сервера теперь ждёт занятый apt до 5 минут (`DPkg::Lock::Timeout`). Ручной путь («Скопировать скрипт») остался.
- **Серверная сторона:** правила базы (репозиторий `index.html`: `gatewayAccounts`, `gatewayBlocks`, `gatewayBlockedDevices`), Worker `POST /gateway-block` и вкладка «Gateway Plus» в приложении «Лаунчер» админ-панели (репозиторий `battle-admin-bot`, v5.35) — блокировка с причиной, разблокировка, список аккаунтов. Подробности и ограничения — в их CLAUDE.md.
- **Честные границы:** (1) **Блокировка — это отказ плагина работать, а не защита от умелого человека**: корень базы открыт на запись, правила не умеют запретить удаление, так что знающий свой номер может стереть свою запись блокировки (тест правил фиксирует это строкой), а подменить сам плагин или просто взять конфиг WireGuard и включить его в обычном WireGuard можно всегда — сервер принадлежит самому человеку, мы до него не дотянемся. (2) **Коммерческое использование плагин увидеть не может** — VPN работает на сервере человека; бан — решение владельца по жалобе/находке, в панели есть кнопка. (3) **«Отдельная база Firebase» пока не создана**: узлы лежат в общей базе проекта (`Cloud.DefaultDbUrl`), закрытые правилами. Настоящая отдельная база со строгими правилами (там можно закрыть запись и удаление блокировок целиком) требует нового проекта Firebase (Spark) — его создаёт только владелец; для переключения нужны `databaseURL` нового проекта и ключ его сервисного аккаунта секретом для Worker'а (Worker сейчас пишет только в основную базу). (4) Мастер **не покупает сервер** за человека и не знает хостеров; облачные файрволы хостера (порт 51820/udp) человек открывает сам — мастер лишь напоминает.
- **Проверка:** `--selftest` на Windows-раннере (сценарий `gateway`): ключ/номер/шифрование/очистка, правила, мастер без подключения, облако против подставного сервера на этом компьютере (регистрация, пульс, блокировка аккаунта и компьютера, «нет связи — остаётся заблокирован»), плюс прежние проверки WireGuard. **Мастер против настоящего sshd** — сценарий `gateway-ssh` в `test-windows.yml` (Ubuntu): `Plugins/GatewayPlus.SshTest` берёт тот же `Provisioner.cs`/`Store.cs`/скрипт и проходит: недоступный порт, неверный пароль, отпечаток (первый раз / знакомый / изменился / отказ; сверка с `ssh-keygen -lf`), настоящая установка по ключу под обычным пользователем с sudo (WireGuard реально ставится и поднимается на машине GitHub), повторный запуск. **Не проверено без владельца:** настоящий хостер (Hetzner и т. п.: свои файрволы, образы), вход по паролю на реальном VPS, скорость и утечки DNS/IPv6, вид окон на его экране.

## Gateway Plus 2.5.0: как ускорить VPN (лаунчер 1.44.0)
Запрос владельца: «найти способ ускорить VPN». Что выяснено и сделано, честно:
- **BBR на сервере не ускоряет «проходной» трафик.** Алгоритм перегрузки работает у того, кто сам держит TCP-соединение; VPN-сервер только пересылает пакеты, а соединение — между вашим компьютером и сайтом. Поэтому BBR (1.42.0) остаётся (полезен самому серверу), но на скорость VPN почти не влияет. Реальные причины медленного VPN: (1) **размер пакета (MTU) для вашего подключения** — у многих провайдеров (DS-Lite, PPPoE, мобильные сети) пакеты WireGuard по умолчанию «не пролезают» и дробятся; (2) IPv6 «в тупике» — у программ с IPv6 первая попытка уходит в туннель без IPv6, ждёт и только потом переходит на IPv4 (страницы «тормозят»); (3) медленный сам сервер или его канал (тариф хостера); (4) на сервере нет быстрой пересылки UDP (ядро < 6.2); (5) WireGuard работает не в ядре, а программно.
- **«Скорость и размер пакета…»** (`SpeedWindow.cs`, `Speed.cs`; пароль от сервера не нужен): (а) замер скорости (Cloudflare `speed.cloudflare.com`: задержка, скачивание 4 потоками 8 с, отдача 3 потоками 6 с, страна/узел) — «так, как идёт трафик сейчас» (с VPN и без — нажать дважды и сравнить); (б) **подбор MTU**: пинг без разбиения пакетов (`PingOptions.DontFragment`, бинарный поиск 1200–1472 байта данных) до сервера из профиля (если шлюз выключен и сервер не отвечает на пинг — до 1.1.1.1 / 8.8.8.8; при включённом шлюзе запасные адреса не берутся — мерили бы сам туннель), рекомендуемый MTU WireGuard = путь − 60 (IPv4) или − 80 (IPv6), в пределах 1280–1420, кнопка «Применить MTU N к профилю» (`Store.WithInterfaceValue`, профиль перезаписывается, вступает в силу при следующем подключении).
- **«Проверить и ускорить сервер»** (`tune-server.sh`, кнопка в окне «Телефон и ускорение сервера…») теперь ещё: (1) **быстрая пересылка UDP** (`ethtool -K <интерфейс> rx-udp-gro-forwarding on rx-gro-list off`, нужно ядро 6.2+, иначе честно пропускается; навсегда — строка `PostUp = … || true` в `wg0.conf`); (2) **IPv6 внутри туннеля**, только если у сервера есть свой IPv6 (маршрут по умолчанию и ответ `api6.ipify.org`): ULA-сеть `fd66:6761:7465::/64` (сервер `::1`, устройство с адресом `10.x.y.N` получает `::N`), `ip6tables` NAT + подгонка MSS отдельными строками `PostUp/PostDown … || true` (сбой IPv6 не должен ронять VPN), `net.ipv6.conf.all.forwarding=1`, перезапуск туннеля; **если после перезапуска туннель не поднялся — настройки возвращаются из `wg0.conf.bak-ghostshell-v6`**. Скрипт печатает `GS_IPV6_PREFIX=…`; плагин (`DeviceWindow.Tune` → `Store.WithIpv6`) дополняет профиль на компьютере адресом `…::N/128`. Телефонные профили остаются IPv4 (новые устройства после включения IPv6 получают оба адреса, `add-device.sh`). Без своего IPv6 у сервера туннель остаётся как был (программы быстро уходят на IPv4). `server-setup.sh` делает то же при установке.
- **Проверка:** `bash -n`, прогон скриптов с подставными командами, на настоящем sshd и WireGuard в `gateway-ssh` (шаги 10–11: строки про UDP и IPv6, принудительный IPv6 через `GS_FORCE_IPV6=1` — либо включился целиком, либо аккуратный откат, туннель жив; новое устройство получает IPv6; повторный запуск ничего не дублирует), чистые функции (`WithInterfaceValue`, `WithIpv6`, `RecommendedWgMtu`) и подбор MTU до 1.1.1.1 в `--selftest` на Windows-раннере. **Не проверено без ПК владельца и без его сервера:** сколько это реально прибавит (зависит от провайдера, сервера и хостера), поведение IPv6 на сервере с настоящим IPv6, работа пинга с DF у него (некоторые сети его режут — тогда плагин честно пишет, что подобрать нельзя). Если скорость самого сервера мала («Скорость самого сервера в интернет» в журнале) — VPN быстрее него не станет: другой тариф или хостер.

## После обновления плагин запускается снова (лаунчер 1.43.2)
Владелец: «когда я обновляю плагины, некоторые отключаются — пусть после обновления запускаются автоматически». Причина: перед заменой файла лаунчер просит плагин выйти (событие `GhostShell.Plugin.Quit.<id>`), плагин возвращает всё, что менял (панель, обои, курсор…), закрывается — а обратно его никто не запускал.
- `NativeInstaller.Install` теперь **запоминает, работал ли плагин** (`IsRunning`), и после замены файла запускает его снова (`Relaunch`): плагины из `Boot.BackgroundIds` (Taskbar Plus, Wallpaper Plus, Cursor Plus, Color Plus) — тихо, с `--background` (они сами применят сохранённое и, если делать нечего, сразу выйдут); плагины только с окном (Icon Plus, DNS Plus, Gateway Plus, Skin Loader) — открывается их окно. Плагин, который не работал, после обновления **не запускается**. `Install` возвращает `true`, если запустил; в сообщении лаунчера «… — запущен снова». Новому плагину с режимом `--background` — добавить id в `Boot.BackgroundIds`, иначе он вернётся с открытым окном.
- **`AskPluginToQuit` просит повторно** (раз в 1,5 с, до 20 с, как `Plugins.AskQuit` в Skin Loader) и вызывается **не в потоке окна** (`Task.Run`): событие выхода создаёт сам плагин при старте, только что запущенный его ещё не создал (проверка на раннере упёрлась именно в это: «Закрой Icon Plus и повтори»). Плагин обязан реагировать на это событие — **у DNS Plus его не было** (обновление при открытом окне не проходило), добавлено в 1.0.6.
- **Проверка:** `BattleLauncher.exe --selftest-update=<папка>` (`NativeInstaller.SelfTestUpdate`, шаг в сценарии `browser`, ветка `ci-e2e-browser`): настоящий релиз Icon Plus → ставится (не запущен — не запускается) → запускается → обновляется поверх работающего → работает **новый процесс** → выход по событию → обновление выключенного его не запускает; аргументы `--background` у фоновых плагинов. **Не проверено без ПК владельца:** возврат эффектов самих фоновых плагинов после обновления на его Windows (на раннере у них нечего применять — они сразу выходят); сам `--background` каждого плагина проверен раньше (сценарии `plugins`, `cursor`, `wallpaper`, `colorplus`).

Исключённые сайты и выключенное расширение — правило снимается. Правило языка (id 1) осталось прежним.
- **Версия Firefox — оценка:** `Firefox/<Chrome major + 3>.0` (оба выходят раз в 4 недели, по датам выпусков 2025 года разница была 3); версия Safari — константа `SAFARI` в `ua.js` (раз в полгода освежать). Это не «настоящие» числа, а правдоподобные.
- **Честные границы:** (1) это **подмена, а не изменение браузера**: сайты с глубокой проверкой всё равно узнают Chromium (шрифты, размер экрана, набор функций движка, поведение API, `window`-свойства, Workers — в Web/Service Worker подмена `navigator` не ставится, их заголовки меняются, но `navigator.userAgent` внутри воркера настоящий); расхождения («Windows» в User-Agent, но шрифты Mac) видят антифрод-сервисы вроде pixelscan. (2) Смена мобильных систем (Android/iOS) намеренно не сделана — страницы переключаются на мобильную вёрстку, а размеры экрана и касания остаются настольными. (3) IP, страна по IP, провайдер и DNS по-прежнему не меняются.
- **Проверка:** `tests/mask-plus/run2.js` (настоящий Chromium, 55 проверок): Safari/macOS, Edge/Windows 11, Chrome/Windows 10, Firefox/Linux — `navigator.*`, `userAgentData`, `getHighEntropyValues`, **заголовки на локальном сервере** (User-Agent и sec-ch-ua совпадают со страницей), iframe, «как родное» в `toString()`, исключённый сайт, выключение, окно (выбор сохраняется, Safari ставит macOS). `run.js` (49 стран) — 48 совпали полностью (AZ — известное расхождение данных ICU). **Не проверено без ПК владельца:** его настоящий Chrome/Edge и конкретные сайты (whoer.net, pixelscan и т. п.).

- **Теперь** (`styler.cpp`, `Relayout`): для форм `pill`/`tab` после расчёта расположения у каждого хозяина считается `barL/barR` = `min(side, левый край значков − pad)` / `min(side, ширина − правый край значков − pad)`, `pad = max(8, islandPad)`; плашка **только расширяется** (отступ из настроек — верхняя граница), `ApplyBar` берёт отступы через `BarSides` (по родителю фона = хозяину), смена отступов — `ReapplyBars`. `Relayout` теперь работает и когда нет островов/расположения, но плашка включена (`wantCover`); если острова больше не нужны, лишние `Border` убираются (раньше при «только расположение» оставались).
- **Статус движка** (`taskbar-plus-engine-status.txt`): новая строка `cover=<левый край значков>,<правый край значков>,<левый отступ плашки>,<правый отступ плашки>,<ширина панели>` — по ней видно, накрыла ли плашка значки (плашка = `отступ_слева .. ширина − отступ_справа`). Тест `taskbar` (`taskbar-states.ps1`, раздел «плашка накрывает значки») на экране 1024 px ставит отступ 486 для `pill` и `tab` и проверяет по `cover`, что значки внутри плашки.
- `GS_ENGINE_VERSION` / `XamlEngine.EngineVersion` = «6» (старая DLL висит в Проводнике до его перезапуска — плагин сам предложит перезапустить панель).
- **Не объяснено:** второй снимок владельца (того же дня) — плашка пустая, значков на ней нет вообще (ни на плашке, ни рядом в обрезке). Причину по снимку установить нельзя; проверять по свежему отчёту Taskbar Plus (`admin-logs/plugin-reports.json`: `apps`, `cover`, `sessions`; в журнале владельца последние подключения дают `подписка на дерево элементов: 0x8000FFFF`, то есть дерево этих окон XAML не приходит).

## Менеджер обновлений: плашка с очередью (лаунчер 1.45.0)
Запрос владельца: «добавить плашку или что-то подобное, где пишется, что в очереди, что сейчас останавливается и всё такое — какой-то менеджер обновлений».
- **Очередь** (`Services/Ops.cs`, `OpQueue`): все установки, обновления и удаления (приложения, EXE-версии, плагины, расширения для браузера) идут **строго по одной** — два плагина, которые меняют панель задач, не останавливаются и не запускаются одновременно. `Enqueue(key, title, kind, run)` не создаёт дубль, если такая операция уже ждёт или идёт (повторное нажатие кнопки); операция получает `OpItem` и сама рассказывает, что делает: `SetPhase(...)`, `SetPercent(...)`, `SetNote("запущен снова")`, `Fail("причина простыми словами")` (и возвращает `false`). Состояния: В очереди → В работе → Готово / Не вышло / Отменено. Отменять можно **только ожидающих** (`Cancel`, `CancelQueued`) — уже идущая на полпути меняет файлы. Окно получает только снимки (`Snapshot()` → `OpView`) и сигнал `Changed` (в поток окна его доставляет `post`, окно перерисовывает не чаще раза в 150 мс — процент скачивания приходит сотни раз).
- **Подписи шагов** (необязательный параметр `Action<string>? phase` у `NativeInstaller.Install/Uninstall`, `Installer.Install`, `BrowserInstaller.Install`): «Останавливаю плагин…» (только если он работал) → «Скачиваю N%» → «Заменяю файл…» → «Записываю ярлыки и версию…» → «Запускаю снова…» (если работал); у Electron-приложений — «Устанавливаю (тихо, может занять минуту)…»; у расширений — «Распаковываю и проверяю…». **В окне подписи доставляются через `Progress<string>` (`PhaseSink`), а не напрямую**: проценты тоже идут через `Progress<int?>`, и прямой вызов обгонял бы их (подпись «Скачиваю 99%» залипала бы на время замены файла).
- **Окно** (`MainWindow.Ops.cs` + `OpsDock` в `MainWindow.xaml`, строка под содержимым правой колонки): заголовок («Идёт работа · готово 2 из 5»), «Сейчас: …», «Дальше: …», общий прогресс, список строк (метка состояния, название · вид, фраза или причина ошибки, «Убрать» у ожидающих), кнопки «Свернуть/Подробнее», «Отменить очередь», «Закрыть». Плашка сама появляется, когда что-то начинается, после конца остаётся 12 секунд (с ошибкой — пока не нажмут «Закрыть»); кнопка «☰ Очередь» в боковом меню (с числом активных) открывает её всегда — там же история запусков («Запустить все» записывает `OpsNote`). Карточки в списках тоже показывают ту же фразу вместо «Работаю…» (`BusyText`: «В очереди…», «Заменяю файл…»).
- **«Обновить все»**: сначала читает, что вышло нового (ничего не трогая), потом ставит **всё найденное в очередь одним махом** (видно весь список сразу), потом ждёт `Task.WhenAll`. Новая операция в окне = `RunOp(key, title, kind, render, body)` (ставит `busy[key]` сразу, чтобы карточка не давала нажать второй раз, и снимает его после).
- **Проверка:** `BattleLauncher.exe --selftest-ops=<папка>` (`OpsSelfTest`, шаг в сценарии `browser`: порядок «по одной», дубли, отмена ожидающих, идущую отменить нельзя, исключение и `false` → причина, «Очистить», ограничение истории 40, подписи фаз); снимок `launcher-9-ops.png` (режим `--screenshot`, выдуманная очередь). **Не проверено без ПК владельца:** как плашка выглядит в живую при настоящем обновлении десятка плагинов и как ведёт себя на узком окне.

- **Схема 3.0** — три независимые части, у каждой одна работа:
  1. **Движок в Проводнике** (`Engine/`, DLL `GhostShellTap`, версия 7; подключение к XAML и `main.cpp` прежние, проверенные; **`styler.cpp` написан заново, ~450 строк**): пока включён — родной фон панели (`Rectangle#BackgroundFill`) прозрачный, тонкая линия (`#BackgroundStroke`) скрыта; и ИЗМЕРЯЕТ положение значков (`TransformToVisual(корень)` × `XamlRoot.RasterizationScale` → пиксели окна панели) в файл `%APPDATA%\BattleLauncher\taskbar-plus-geometry.txt` (формат в `Geometry.cs`; раз в 100 мс при изменениях и раз в секунду как «жив»). Панель = корень XAML, в котором есть `Taskbar.TaskbarFrame` (всплывающее окно скрытых значков — другой корень, его не трогаем). Системная область = рамка `SystemTray.SystemTrayFrame`; виджеты = по **видимому содержимому** (текст/картинки/значок), а не по всей кнопке (у неё бывает широкая пустая область под бегущие строки). Встроенные правила — `BuiltinRules()`; правила из настроек (`engine-rules.txt` на GitHub) только **добавляются**. **«Выключатель мёртвой руки»:** плагин переписывает `taskbar-plus-engine.cfg` каждые ~3 с; если файл не обновляли 20 с (плагин закрыт аварийно/завис) — движок сам возвращает родной фон (`alive=0`, `applied=0` в статусе). Родной фон панели прозрачный → плашки видны сквозь неё, значки и часы рисуются поверх. ## GSP — свой VPN-протокол «Ghost Shell Protocol» (`Protocols/Gsp/`, этап 1, ещё не в интерфейсе Gateway Plus)
Запрос владельца: «если есть такая возможность, хочу собственный протокол — вдруг он будет эффективнее, и можно строить свои функции». Сделан рабочий прототип на Go (один бинарник `gsp`: сервер и клиент по настройкам, Linux + Windows, `go test` + стенд сравнения; в лаунчер/плагин **пока не встроен** — это этап 2).
- **Своей криптографии нет** (это правило проекта: самодельное шифрование почти всегда с дырами). Только проверенные кирпичи: рукопожатие **Noise IK** (`github.com/flynn/noise`, Curve25519 + ChaCha20-Poly1305 + BLAKE2s, как в WireGuard), данные — **ChaCha20-Poly1305** со счётчиком в nonce и окном повторов на 2048 пакетов, ключи заголовков — BLAKE2s от ключа сеанса. Новое здесь — только упаковка пакетов и защита от потерь.
- **Что отличает от WireGuard:** (1) **защита от потерь (FEC, код Рида — Соломона, `fec.go`)**: на каждые K пакетов — M проверочных, до M потерянных из группы восстанавливаются без повторной отправки; данные идут сразу (задержки нет). `FEC = off | auto | K+M`; в `auto` приёмник раз в секунду шлёт отчёт «дошло/ожидалось» (`frReport`), отправитель включает защиту по таблице `fecLevelFor` (цель — после восстановления терять ≤ ~0,05%) и держит её ещё 15 с после затишья; без потерь стоит ноль (только 1 пакет в секунду на отчёт). (2) **Пакеты выглядят случайным шумом**: рукопожатие упаковано XChaCha20-Poly1305 с ключом из открытого ключа сервера и случайной набивкой 0–255 байт (разные длины, чужой пакет не получает ответа вообще), у пакетов данных первые 12 байт (индекс и счётчик) замаскированы как «защита заголовка» в QUIC; `Pad = N` добавляет случайную набивку к каждому пакету. Постоянных байт-сигнатур нет. (3) **Статус-файл** (`-status файл`, раз в секунду JSON: потери, включённая защита, восстановлено, трафик, возраст сеанса) — для окна плагина.
- **Как устроено** (файлы): `crypto.go` (сеанс, маска заголовка, окно повторов, упаковка рукопожатия), `handshake.go` (Noise IK; ответ сервера, ключи), `fec.go`, `engine.go` (приём в 3 стадии «сеть → расшифровка → TUN», отправка в 2 стадии «TUN+шифрование → сеть», UDP GSO на Linux, таймеры, маршрутизация по ключам: пакет принимается, только если его адрес-источник разрешён этому собеседнику), `config.go` (файл как у WireGuard: `[Interface]`/`[Peer]`, лишние строки вроде `PostUp` **отклоняются**), `gso_linux.go`, `ifup_linux.go` (адрес/MTU командой `ip`; на Windows адрес и маршруты поставит служба-обёртка — этап 2), `main.go` (`gsp genkey|pubkey|run -c файл`). Сетевая карта — `golang.zx2c4.com/wireguard/tun` (на Windows нужен `wintun.dll`). Смена ключей каждые 120 с (рукопожатие начинает клиент), «связь пропала» — через 30 с без ответа; `PersistentKeepalive` как в WireGuard.
- **Тесты** (`go test -race`, 11 штук, без сети и TUN): окно повторов, рукопожатие и обмен, чужой ключ сервера / неизвестный клиент не получают ответа, подделка адреса-источника отбрасывается, повторённый пакет отбрасывается, защита от потерь на прокладке с потерями 5%, разный размер пакетов рукопожатия, разбор настроек. **Стенд сравнения** `bench/run.sh <каталог с бинарниками> [потери,%] [задержка, мс в сторону] [секунд] [cubic|bbr|reno]`: три сетевые «комнаты» (клиент — прокладка `tools/relay` — сервер), настоящий TUN, `iperf3` вниз и вверх через wireguard-go, WireGuard в ядре (если есть), GSP без защиты / auto / 10+2 / 8+3. Workflow `gsp.yml` гоняет всё это на машине GitHub при каждом пуше в `Protocols/Gsp/**` (там WireGuard в ядре есть — третья точка сравнения) и собирает бинарники под linux/amd64, linux/arm64, windows/amd64 (артефакт `gsp-binaries`). **Важно для стенда:** `net.ipv4.tcp_congestion_control` в этой среде — `bbr`, он почти не чувствителен к потерям и скрывает разницу; сравнивать только с `cubic` (так по умолчанию у Windows и большинства серверов).
- **Честные результаты** (стенд `bench/run.sh`, машина GitHub `ubuntu-latest`, 4 ядра, `iperf3` с CUBIC, MTU 1380; цифры — «вниз / вверх», Мбит/с; потери случайные и равномерные, задержка 20 мс в каждую сторону): **без потерь** — WireGuard в ядре 1102 / 1121, wireguard-go 4566 / 4618, **GSP 1465 / 1463** (с включённой защитой 1120–1200: плата за проверочные куски). То есть **по чистой скорости GSP быстрее ядерного WireGuard на этом стенде (оно считает по пакету, без укрупнения), но втрое медленнее wireguard-go** (тот использует «укрупнение» TCP в TUN и параллелизм); любому домашнему каналу и VPS на 1 Гбит/с хватает всех трёх. **С потерями** (то, ради чего затевался GSP): при **1%** — WireGuard ядро 4,3 / 3,5, wireguard-go 3,4 / 4,7, **GSP auto 6,2 / 12,5, GSP 8+3 16 / 23**; при **3%** — 1,4 / 1,7, 1,5 / 1,7, **auto 5,6 / 14,2, 8+3 6,6 / 17,7**; при **8%** — 1,2 / 1,0, 0,6 / 0,7, **auto 6,3 / 23,9, 8+3 8,1 / 6,0**. GSP без защиты ≈ WireGuard (защита — единственное отличие). Вывод: GSP **не быстрее** WireGuard на хорошем канале, зато при потерях 1–8% даёт **в 3–20 раз больше** (внутренний TCP не пугается потерь). Оговорки: потери в стенде случайные и независимые, в жизни они пачками (Wi-Fi, мобильная сеть) — выигрыш будет другим, а при пачках длиннее M защита бессильна; защита добавляет 25–60% трафика, пока включена; скорость при потерях всё равно далека от полной; **на настоящем сервере и канале владельца не измерялось.** Разброс между прогонами заметный (в 1,5–2 раза), особенно у «auto» (ему нужно несколько секунд на включение).
- **Известные границы:** только IPv4-адрес сервера (внутри туннеля IPv6 разрешён); нет защиты рукопожатия от перегрузки (cookie, как у WireGuard) — для личного сервера терпимо; нет запасного режима «через TCP/443» для сетей, где UDP закрыт; рукопожатие подписано ключом, выводимым из открытого ключа сервера, — это **маскировка**, а не секрет (кто знает открытый ключ, может послать init, но Noise всё равно проверит клиента); маскировка от умной системы глубокого анализа (DPI) не проверялась; ни одной проверки на настоящем сервере и на Windows с `wintun` ещё нет (на Windows CI пока только сборка и тесты движка).
- **Этап 2 (не сделан):** встроить в Gateway Plus — выбор протокола («WireGuard» по умолчанию / «GSP»), мастер ставит `gsp` на сервер по SSH (скачать бинарник из релиза, проверить sha256, systemd-служба, NAT, порт в файрволе), Windows-клиент как служба (`wintun.dll`, адрес/маршруты/DNS через `winipcfg`), профили под DPAPI, окно показывает статус-файл (потери, включена ли защита). Дальше возможны: запасной TCP/443, ротация портов, раздельное туннелирование по программам/доменам, сжатие. **Не придумывать собственную криптографию** — только комбинировать проверенное.
